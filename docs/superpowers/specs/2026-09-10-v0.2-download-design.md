# v0.2 — Download linters, runtimes, and other tools

Design for ROADMAP.md's v0.2 milestone: `rtunk download`, `rtunk exec|x`, `rtunk where`, `rtunk
cache clean|prune`. Builds directly on v0.1's `pkg/trunk/config` (parsed/resolved trunk.yaml +
plugin definitions) — nothing here touches config parsing.

## Goals

- Fetch the tool/runtime binaries a resolved config references, hermetically and
  reproducibly, per AGENTS.md's non-negotiable rules (zero telemetry beyond the explicit fetch,
  checksum-verified, content-addressed cache, HTTPS only).
- `rtunk download` with no arguments fetches everything currently enabled (+ transitively
  referenced) in the resolved config — the common case. `rtunk download <category> <id>[@version]`
  targets one item.
- Expose fetch progress as a stream of events, not just a final success/failure, so the CLI (and
  any future consumer) can render start/progress/done/error per item as it happens.

## Non-goals (this milestone)

- Executing linters/actions against source (`v0.3`+).
- Package-manager-based fetch for any runtime other than `node` (see "Fetch mechanisms" below) —
  other runtime types return an explicit "not yet supported" error rather than a guess, since
  trunk's own per-runtime install commands aren't part of the open plugin schema.
- A cross-machine/checked-in checksum manifest (see "Checksum model").

## Package layout

New `pkg/trunk/download`, sibling to `pkg/trunk/config`: owns cache layout, HTTP fetch, archive
extraction, shim creation, and checksum/content-addressing. CLI wiring lands in
`internal/cli/{download,exec,where,cache}.go`, mirroring the existing shape of
`internal/cli/config.go`.

Runtime-specific package-install logic gets its own file per runtime type —
`pkg/trunk/download/runtime_node.go` today, `runtime_python.go`/`runtime_go.go`/... whenever a
later milestone adds them — so adding a runtime never touches another runtime's file. A small
dispatcher (`runtime.go`, plain `switch runtime.Type`) routes to the matching file's function; no
registry or interface, since v0.2 ships exactly one real case and a `switch` says everything a
one-method interface would.

## Cache layout

Rooted at the same `--cache-dir` / `RTUNK_CACHE_DIR` the CLI already exposes (`internal/cli/cli.go`
`CLI.CacheDir`), which today points only at the plugin-source cache (`pkg/trunk/config/git.go`
`fetchGitSource`). This milestone re-roots it as a shared cache root with two subtrees:

```
<root>/
  plugins/            # existing plugin-source cache (git.go) -- unchanged, just re-rooted
  downloads/
    blobs/sha256/<hex>                             # raw fetched bytes, content-addressed
    installs/
      runtimes/<type>/<version>/<platform>/        # a downloaded runtime, e.g. node/22.18.0/darwin-arm64/
      tools/<id>/<version>/<platform>/             # download-recipe: binary sits here directly
                                                     # runtime+package: npm --prefix target here ->
                                                     #   node_modules/.bin/<name>, node_modules/<pkg>/
    shims/<category>/<id>/<version>/<shimname>
```

**In-scope fix to existing code:** today `git.go`'s `fetchGitSource` appends `/plugins` itself only
when `cacheDir` is empty (the OS-default case); an explicitly-passed `--cache-dir`/`RTUNK_CACHE_DIR`
is used as the plugin cache dir directly, with no `/plugins` suffix. This milestone normalizes both
cases to treat `CacheDir` as the shared root and always append `/plugins`, so `downloads/` can be
its sibling regardless of whether the cache dir came from a flag or the OS default.

Each tool/runtime install directory is keyed by `<id>/<version>/<platform>` (`platform` =
`GOOS-GOARCH`, e.g. `darwin-arm64`), since a hermetic install is platform-specific.

## Checksum model (trust-on-first-use)

The plugin schema (`downloads:` recipes) carries no upstream checksums at all — trunk-io/plugins
never ships a SHA256 alongside a `url:`. AGENTS.md's "checksum-verified downloads" is therefore
rtunk's own guarantee, not verification against something upstream provides.

Mechanism: a blob's storage path under `blobs/sha256/<hex>` _is_ the SHA256 of its bytes, computed
by streaming the HTTP response through a hasher into a temp file, renamed into place only once the
hash is known. Nothing downstream (extraction, shim creation) ever reads from a path whose name
doesn't match its own content — corruption or an incomplete write is structurally impossible to
mistake for a good artifact.

`ponytail:` this catches corruption/tampering-at-rest on a single machine but each machine
computes and trusts its own first download independently — there is no shared, pinned-ahead-of-time
manifest checked across machines or CI runs. Upgrade path if reproducible cross-machine pinning is
ever needed: a checked-in `rtunk.lock` (`id@version@platform -> sha256`), verified against on every
fetch the way `go.sum` is.

## Download engine API

```go
package download

// Ref identifies one item to fetch. Version "" defers to whatever trunk.yaml/the resolved config
// pins for that id.
type Ref struct {
    Category string // "tools" | "runtimes" | "lint" | "actions" | "plugins"
    ID       string
    Version  string
}

type Phase int

const (
    Started  Phase = iota // fetch beginning for this ref
    Progress               // bytes received so far (HTTP fetches only; npm installs skip straight to Done)
    Cached                 // already present locally (or system_version runtime); nothing fetched
    Done                   // fetch + extract/install + shim complete
    Failed                 // Err is set
)

type Event struct {
    Ref          Ref
    Phase        Phase
    Bytes, Total int64 // Progress only; Total -1 if the server didn't send Content-Length
    Err          error // Failed only
}

// Download fetches refs into cacheDir. An empty refs list means "everything enabled and
// transitively referenced" in cfg (mirrors config.Resolve's filterEnabled semantics) -- what bare
// `rtunk download` runs. It returns immediately with a channel of lifecycle events, closed once
// every ref has reached Done/Failed/Cached; a non-nil error return is a setup failure only (e.g.
// an unwritable cacheDir), never a per-item failure -- those are Failed events on the channel.
func Download(cfg config.Config, cacheDir string, refs ...Ref) (<-chan Event, error)
```

A small fixed-size worker pool bounds concurrent fetches (avoid hammering upstream registries with
one goroutine per item on a large `rtunk download`). `ponytail:` pool size is a constant for now;
add a `--parallel` flag if someone actually needs to tune it.

## Fetch mechanisms

**`download:` recipes** (most runtimes, standalone-binary tools like `shellcheck`): pick the
`DownloadEntry` matching `runtime.GOOS`/`GOARCH` via `OSSpec`, template `${version}`/`${os}`/`${cpu}`
into the URL, HTTPS GET with `Progress` events as bytes arrive, extract (tar.gz/tar.xz/zip inferred
from the URL's extension) honoring `strip_components`, `chmod +x` when `Executable: true`, write the
shim(s) named by `Shims`.

**`runtime:` + `package:` tools**: ensure that runtime is downloaded first (recursing into the same
`Download` machinery), then install the package through it. This milestone implements `node` only —
`runtime_node.go`'s install function runs `npm install --prefix
installs/tools/<id>/<version>/<platform>/ <package>@<version>`. Any other runtime type (`python`,
`go`, `ruby`, …) has no file yet, so the `runtime.go` dispatcher's `switch` falls to an explicit
`fmt.Errorf("package-based fetch not yet supported for runtime %q", runtime.Type)` rather than
guessing an install command — adding real support later means adding that runtime's own file, not
touching this one.

A runtime-based tool's shim differs from a download-recipe shim: instead of a symlink straight to a
binary, it's a small wrapper that (1) locates the tool's runtime install dir, (2) builds `PATH` from
the runtime's `RuntimeEnvironment`/`LinterEnvironment` entries (already parsed in
`pkg/trunk/config`, e.g. prepending `node_modules/.bin` and the runtime's own `bin/`), then (3)
`exec`s the real target under `node_modules/.bin/<name>` with args passed through — needed because
an npm-installed bin is a script with a `#!/usr/bin/env node` shebang that must resolve `node` on
`PATH` at run time.

**`system_version` runtimes** (e.g. `php`): never downloaded. `Download` emits `Cached` immediately;
actually confirming the host has a satisfying version is deferred to `check` (a later milestone that
runs `version_commands`).

## CLI surface

- `rtunk download [<category> <id>[@version]]` — bare form downloads everything enabled+used;
  with a category+id, one targeted item. Renders one line per `Event` to stdout as it arrives.
- `rtunk exec|x {tools,runtimes} <id>[@version] -- <args>` — downloads via the same engine first if
  the shim isn't already cached, then executes the shim with `args`, inheriting stdio.
- `rtunk where {plugins,lint,actions,tools,runtimes} <id>[@version]` — prints the shim's filesystem
  path. Never triggers a download; errors ("not downloaded, run `rtunk download` first") if the item
  isn't already cached.
- `rtunk cache clean` — `os.RemoveAll(cacheDir/downloads)`.
- `rtunk cache prune` — resolve enabled+used (reusing `filterEnabled`, already in v0.1) and delete
  every blob/install/shim under `downloads/` not referenced by that set.

## Testing

- `pkg/trunk/download`: table-driven unit tests per concern — URL templating/`OSSpec` matching,
  content-addressing round-trip (write → verify path == hash), extraction with `strip_components`,
  npm install command construction — against `httptest.Server` for the HTTP paths, never real
  network.
- One `internal/cli` test per new subcommand (`download`, `exec`, `where`, `cache clean`, `cache
prune`), wired against a fake local HTTP server + temp cache dir, asserting the emitted event
  sequence and/or resulting cache layout, matching the existing `internal/cli` test shape.
